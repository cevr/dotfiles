# Nothing is hard, in the role prompts

The owner's standing rule, "nothing is hard", reaches every orchestrate role agent (planner, implementor, verifier) and the lean worker in its prompt. How a step ends is one versioned round policy (`mods/orchestrate/round-policy.ts`, which ships with the plugin; `skills/orchestrate/scripts/round-policy.ts` places it in each host's prompt): its rows, verdict rules and stop evidence are data, rendered into each prompt as one strict block and decoded back from what each host delivers. Each item is a record decided by its own history: assigned to the role or not, required or an optional probe, its attempt history (never attempted, or the last attempt's result: none yet, pass, fail, unclear), whether a result settles it, its current obstacles as a set (refused, the host cannot run it, a live wait: any of them at once), and a verifier finding's provenance. A validity rule rejects a record only with its justification, two definitions that exclude each other or no history reaching it, and the records `skills/orchestrate/scripts/item-histories.ts` reaches by generating every event sequence equal the valid ones; and each state is a conjunction of facts, so every valid item is in exactly one state (enumerated per role). F1 gives each item its one label from that state (done, runnable, waiting, refused, cannot run, for a verifier proven, ran unclear or unproven, and work outside the assignment, which a verifier marks `unit` or `base` by measured attribution), whatever stopped the step; an optional probe is only ever done, proven or unproven and never changes the verdict. F2 gives the verdict from the item states present, by a stated precedence (a verifier is `stuck` while any required check is runnable, waiting, refused, unable to run or unclear, else `changes` on a proven Blocker or Major, else `accepted`; a planner or implementor is `ready` only when every required item is done, else `blocked` with `state.md` current and `blocked.md`), and the evidence from why the step stopped (a refusal with or without a named form, the round's limit, no runnable item left). An input no step can produce is rejected as ill-formed. Each role's prompt carries it as one generated block (`<!-- round-policy v1 <role>: … -->`): F1 as an ordered table under "Take the first row that is true of the item; stop there.", its last row a catch-all, each condition written in one grammar the test reads back, and the evidence fields as a separate instruction (each field the item's record holds, with its exact values: the last completed attempt's id, command, output digest, exit, receipt and head, a newer unfinished attempt, the refusal's scope and exact form, the missing tool's probe, the wait's ref), never a row; F2 under its own first-row sentence with the files each verdict writes; and a third table of the evidence fields each stop writes. Read back from every prompt, the first true row gives F1's label on every reachable record, every pair of rows both true of one, computed from every reachable record with two or three obstacles at once, has a pinned winner naming the evidence that must survive, a second or third obstacle is named after the label by its own instruction, on an optional probe too (a refused optional probe is refused, since a refusal stops the step whatever the item; a missing tool or a wait leaves it unproven with that obstacle named), and each history's hand-back (label, governing evidence, other obstacles, last attempt exactly when attempted) is judged value by value (`judge`) against the one the decoded policy makes due for its content-bound record (`due`): a flag never stands in for an attempt's content, and a step is admitted (`admit`) only when its verdict, files, stop evidence and every item match its checked records; and every paragraph outside it is pinned by an approved inventory (`skills/orchestrate/prompt-inventory.json`). Difficulty is never a reason; a compaction or a long context does not end the step. A question's options state outcomes with effort on its own `measured` or `guess` line, and its assumption cites its principle by name and is never the lesser option for effort. A weak test, narrowed acceptance or written-rule break goes by where it came from: one the unit's change introduced to the same lane's next round, one the base head shows too to a follow-up unit; none fails a round. The refusal paragraph is word for word what it was, plus "A refusal is authority, not difficulty."; the principle leaves every refusal, with or without a named accepted form, to the role's rule. A follow-up is work no spec item asks for, even inside a file the unit owns. The lean worker is told a refusal is the host's rule and outranks effort, with no bound-step instruction.

## Sub-features

- `NIH1` each role's prompt carries the rule, the hand-back rule and the question form (`skills/orchestrate/protocol.md`, generated into `mods/orchestrate/agents.json`).
- `NIH2` the refusal rule is unchanged but for its one added sentence.
- `NIH3` findings route by provenance: the unit's own to its lane's next round, the base's to a follow-up unit.
- `NIH4` the worker's prompt carries the rule and the refusal-authority reminder, and goes on past a compaction or a long context.
- `NIH6` the prompts reach the agents: a root offered `subagent` and `principles` starts one child of each role, each child's model request carries its role's prompt, its required-work line and the principle's name, and `principles` list and search answer principle-nothing-is-hard.
- `NIH5` the generated prompts match their source: deleting one role's emitted line makes `--check` red.
- `NIH8` each role's and the lean worker's model request, as the scripted model receives it, carries one round-policy block that decodes to exactly its role's policy (every part, then the bytes); a dropped verdict file (`state.md`), a dropped refusal form field and another role's block are each named by the decoder, and `mods/orchestrate/role.ts` decodes every role's policy before it exposes a definition.
- `NIH7` the round policy's outcome is total, the item states partition every valid record of facts per role, each prompt's ordered list read back gives F1's label on every reachable record with only the listed overlaps, over every role, stop and multiset of up to three item states, each prompt carries exactly its role's block, every paragraph outside them is in the approved inventory (an appended, edited, removed or moved paragraph is red until the inventory is rewritten on purpose), and every sentence of the installed prompts the head no longer holds word for word is accounted for in `skills/orchestrate/scripts/retention.ts`.

## How to get to it (user POV)

- An orchestrator starts a role agent: `subagent({ agent: "implementor", ... })` (also `planner`, `verifier`); an untyped or general call runs as `worker`. The prompt it runs on is `mods/orchestrate/agents.json`'s `system` for that agent.
- On Claude Code and Codex the same text is the dotfiles' `agents/<role>.md` and `codex/agents/<role>.toml`.

## Gotchas

- The prose's source is outside `opencode/`: the orchestrate skill's `protocol.md` and `SKILL.md` and the dotfiles' `agents/worker.md`. The round policy's source is inside it, `mods/orchestrate/round-policy.ts`, so the installed plugin ships the very data its prompts were rendered from; `skills/orchestrate/scripts/agents.ts` writes its block into each prompt, `agents/worker.md` and `skills/orchestrate/end-of-step.md`. A change to either shows here only once `bun run agents` rewrites `agents.json`, which is this feature's Code, and `role.ts` refuses to load an `agents.json` whose policies no longer match the source.
- The old `<!-- end-of-step -->` block and `skills/orchestrate/scripts/ending.ts` are gone; a prompt still carrying that block is refused as an unknown version, never read.
- On the installed host the kernel plugin runs with `codeOnly` (its default): a model is offered `kernel` and the memory tools alone, and `subagent` and `principles` are lines in the kernel's description, called from a cell (`cmd/kernel/server.ts` line 145; the fork's `packages/core/src/tool.ts` `runtimeSnapshot`). A scripted model that looks for `subagent` or `principles` among a request's offered tools finds neither there; the world, which hosts no kernel (`kernel.md`), offers them directly.
- This is a prompt rule, not a check of a live run: nothing here bounces a hand-back or a question yet. `due`, `judge` and `admit` are the contract the later units (spec items, hand-back tools, question reasons) call; until then they run only in tests.
