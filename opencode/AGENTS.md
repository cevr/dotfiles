# OpenCode mods

Our harness work, ported onto OpenCode 2.x: the Prime Agent look, orchestration, the account pool, the code kernel.

This folder lives in the PUBLIC dotfiles repo: stage by exact path, keep tokens, account labels and run evidence out of it (`out/` and `media/` are ignored). Run every command from `opencode/`.

Before changing a mod, read `ARCHITECTURE.md`: every mod is an Effect program modeled like an alchemy-domain model and laid out like a Go service. A mod is one context and one workspace package (`mods/<mod>`): domain files at its root that own their contracts, implementation folders inside it named after their dependency, and a `cmd/<mod>` package per plugin as the only composition root. oxlint fences the imports (`bun run lint`); `tests/layout.test.ts` checks the names and lists the mods not yet moved as pending.

## Layout
- `scenarios/`: opencode-drive scenarios. Each runs OpenCode headless with a scripted model and writes frames (text) and screenshots. They are the deterministic check for every UI or plugin change.
- `themes/`, `mods/`: what OpenCode loads from us. `mods/prime` is the Prime look with fx's rail composer and tool-call groups (a header over a `├`/`└` tree per run of calls, after `vercel-labs/fx` as gent copied it: a run is one model step's calls, ended early by answer text, so each kernel cell or batch of parallel calls is its own group and the newest call is the last line, a kernel call draws as the `tools.*` calls its cell made (`kernel.ts`), never its code, and thinking shows only at All), loaded by path through the config's `plugins` as `cmd/prime` (its composition root, `cmd/prime/tui.tsx`). The words each row shows are plain domain files at the mod's root (`group.ts`, `call.ts`, `notice.ts`, `chrome.ts`, ..., over the session values in `session.ts`); the Solid components are in `tui/`, which read the host only through `tui/host.ts`'s `Host`, built from the plugin context in `opencode/host.ts`. Steps that only start background agents, each within a minute of the last, share one group, and worker completion notices that land side by side fold into one line (through the fork's `session.message.completion` slot). A compaction is one line below All (`◇ Compacted automatically · 171k → 6k tokens · 12.0s`, `compaction.ts`: the compaction request's prompt and output tokens, the time to the next message the run writes) and the host's whole block with the summary at All (through the fork's `session.message.compaction` slot, branch `prime-compaction-row` until it lands on `prime-look`). A subagent's row, a finished worker's notice and the dock's subagent count open by click (the row and notice open that session, the count the host's Subagents picker); inside a subagent the top bar names its parent, ↑ goes back and ←/→ move to the other running subagents, and the hint above the composer says so. Beneath the dock's subagent count, one live row per subagent of the family (`tui/live.tsx`, from `mods/subagents`) gives its role, unit, state, a one-sentence update and its time, a finished one lingering 30 seconds, whether or not the host shows the session's sidebar; inside a subagent the rows sit above the host's picker and mark the one shown. The domain imports only `effect` and `@dotfiles/opencode-subagents/*`, and `tui/` never `@opencode/*` or `opencode/` (`.oxlintrc.json` fences); OpenCode provides `@opencode/plugin`, `@opentui/*` and `solid-js` and compiles the TSX, workspace imports included, at load time.
- `mods/subagents`: the subagent rows, plain TypeScript with no plugin of its own. `rows(family, rootSessionID, now)` in `subagent-row.ts` gives each subagent's role, unit, state (running, blocked, done, failed, cancelled, idle), one-sentence update and elapsed time, in launch order, keeping a stopped one `LINGER_MS`; one that ended its turn to wait on its own background shells or subagents (no stop notice yet, read from tool calls and a kernel call's `operations`) or that its parent still waits on runs, `waiting on <command>`; `format(row, width)` in `line.ts` draws one as coloured segments. Its input is the plain `Family` view in `family.ts`, which `opencode/view.ts` reads from a TUI plugin's `context.data`. Prime's live rows use it, and the sidebar Queue is meant to.
- `mods/orchestrate`: the orchestrate skill's rules, a server plugin. It defines the role agents (planner, implementor, verifier, worker) from `agents.json`, runs untyped and general subagent calls as the worker and former role names as the role (logging each call to `~/.cache/orchestrate/opencode-agents.jsonl`), gives each role its compaction window from `~/.cache/orchestrate/compact.json`, and stops agent work over the Sabbath. The window takes effect through the fork's per-agent compaction threshold (`request.settings.compactionWindow`).
  The composition root is `cmd/orchestrate/server.ts`; the model is the `ToolCall` aggregate in `tool-call.ts`, the contracts in `service.ts`, implemented in `filestore/`, `opencode/` and `codex/`. Its model is in the README's Orchestrate section.
- `mods/pool`: the account pool, a server plugin. It chooses the login each request of a pooled provider goes out on, holds a refused login and fails over to another; other mods read it over `status.ts` (`@dotfiles/opencode-pool/status`). The composition root is `cmd/pool/server.ts`; the model is the `AccountPool` aggregate in `account-pool.ts`, the contracts in `service.ts`, implemented in `opencode/` and `gent/`. Its model is in the README's Pool section.
- `mods/status`: the `/pool` pane, a server and a TUI plugin. The server answers the status RPC (`status.ts`) with the live subagents from orchestrate's call log and each orchestrate run's units; the pane (`tui/pane.tsx`) draws them beside the pool's status. The composition roots are `cmd/status/server.ts` and `cmd/status/tui.tsx`; the model is the `AgentCalls` view in `agent-calls.ts` and the handler in `model.ts`, the contracts in `service.ts`, implemented in `filestore/` and `process/`. Its model is in the README's Status section.
- `mods/queue`: the agent's live queue, a server and a TUI plugin. The server adds the `queue` tool (a direct tool, so a kernel cell reaches it as `tools.queue`), keeps each session's queue in a file store and answers the queue RPC (`queue.ts`, `QUEUE`); the sidebar's Queue section (`tui/sidebar.tsx`) shows the route's root session's queue items only, one line each, an item linked to a subagent session marked with that session's live state. The composition roots are `cmd/queue/server.ts` and `cmd/queue/tui.tsx`; the model is the `Queue` aggregate in `queue.ts`, the board in `board.ts`, the contract in `service.ts`, implemented in `filestore/` and `memory/`; `opencode/subagents.ts` maps the shared rows of `@dotfiles/opencode-subagents` to the live state of each subagent session. Its model is in the README's Queue section.
- `mods/git`: the sidebar's Git section and the `/git` pane, a server and a TUI plugin ported from gent's `@gent/git`. The server answers the git RPC (`git.ts`) by running git and `gh` in the session's directory (its location, read per call); the TUI runs no program except the review it hands the terminal to (hunk, else git's pager) through the renderer's suspend and resume. The composition roots are `cmd/git/server.ts` and `cmd/git/tui.tsx`; the parsers are in `checkout.ts` and `pull-request.ts`, the handler in `model.ts`, the contracts in `service.ts`, implemented in `process/` and `opencode/`. `tests/git.test.ts` runs `scenarios/git.ts`. Its model is in the README's Git section.
- `mods/btw`: `/btw`, a side question in the session's panel, a TUI plugin ported from gent's `/btw` with no server half. `/btw <question>` forks the session (`session.fork`, which keeps its cache key) and asks the fork with a hidden note; the pane reads the fork from the server's message list (`opencode/readings.ts`; the TUI's message cache evicts sessions it does not retain), follows up, and ctrl+s brings the newest answer back as a steered synthetic. The fork's built-in `/btw` is off (`-opencode.btw` in `cli.json`). The composition root is `cmd/btw/tui.tsx` (`setup.ts` holds everything but the JSX, for the seam test); the model is the `SideQuestion` aggregate in `side-question.ts`, the handlers in `model.ts`, the contracts in `service.ts`, implemented in `opencode/` and `memory/`, the controller and pane in `tui/`. `tests/btw.test.ts` runs `scenarios/btw.ts`. Its model is in the README's Btw section.
- `decider/` (`@dotfiles/decider`): what the mods' domains share. `decider.ts` is the aggregate's `Decider` type and `fold`; `story.ts` runs a Decider's stories (`Story.make(decider)(given, clock, when, then, rejected, state, view)`).
- `cmd/`: one workspace package per plugin OpenCode loads (`server.ts`, `tui.tsx`); `bun run daily` loads a plugin from `cmd/<mod>` once it exists, else from `mods/<mod>`.
- `mods/anthropic-auth`: the Claude subscription login, vendored from `@ex-machina/opencode-anthropic-auth` (MIT) with our quota readings and the seam the pool chooses each request's credential through; provenance in its README. The composition root is `cmd/anthropic-auth/server.ts`; the domain is one concept per file at the mod's root, the decisions (logins, refreshes, readings) in `model.ts`, the contracts in `service.ts` with their laws in `laws.ts`, implemented in `fetch/`, `node/`, `registry/` and `opencode/`. `cmd/anthropic-auth/server.test.ts` drives the plugin on a stand-in host. Its tests run without `ANTHROPIC_BASE_URL`.
- `mods/kernel`: the code kernel, a server plugin ported from gent's `cell`. The `kernel` tool runs TypeScript in a Bun worker per session (`worker/program.ts`, framed over fd 3 and 4 by `wire.ts`) whose bindings persist and are stored after each call; `tools.<name>()` inside it runs the session's other tools (`opencode/toolbox.ts`), and each call records them, live and in its result's metadata (`operations` in `operations.ts`), for the transcript. The composition root is `cmd/kernel/server.ts`; the model is the `KernelSession` aggregate among the domain files at the mod's root. By default it is the agent's runtime (the fork's `options.runtime`): the model sees only the kernel, and calls go through the registry's hooks. Options and limits are in the README.
- `mods/herdr`: the herdr reporter, a TUI plugin ported from gent's `@gent/herdr`. Inside a herdr pane it reports the current route's root session and its subagents to herdr's socket as idle, working or blocked (source `dotfiles:opencode`, resume `opencode -s <root>`), with the session's title and the running tool as labels. The composition root is `cmd/herdr/tui.tsx`; the decision is `decide` in `activity.ts`, the contract `Herdr` in `service.ts`, implemented over the socket in `herdr/socket.ts`; `opencode/view.ts` reads the TUI's data. `tests/herdr.test.ts` runs `scenarios/herdr.ts` against a fake herdr socket.
- `mods/cache`: prompt-cache misses, a TUI plugin ported from gent's `@gent/cache` with no server half. It folds a session's assistant messages (`opencode/view.ts`) into the prefixes a step was billed for again (`scan` in `miss.ts`, above a 1,024-token floor), gives each its cause over the cache lifetime its agent's request used (`ttl.ts`: the agent's `request.settings.cacheTTL` over a configured `settings.cache.ttl`, else that, else Anthropic 5 min, OpenAI 30 min), naming a pool login move (the pool's `logins` RPC) and a compaction apart from a changed prefix, prices it (`price.ts`), and draws a row after each turn's footer slot for a miss of 20k tokens or $0.10 and a sidebar line `Cache 91% · missed $0.42` for the session and its subagents (`line.ts`, `ledger.ts`, `tui/`). The composition root is `cmd/cache/tui.tsx`; `tests/cache.test.ts` runs `scenarios/cache.ts`.
- `mods/guard`: the destructive-command guard, a server plugin ported from Claude Code's `claude/hooks/guard-destructive.ts` with gent's guard-floor parsing. Its `execute.before` hook refuses a `shell`/`bash` call that loses work for good (recursive `rm` of root, home, the working directory, `.git` or a repository root; `git reset --hard`; a forced wide `git clean`), direct or from a kernel cell. The composition root is `cmd/guard/server.ts`; the decision is `verdict` in `verdict.ts`, the contracts in `service.ts`, implemented in `filesystem/` and `opencode/`. `tests/guard.test.ts` proves both paths in real OpenCode; the rules are in the README's Guard section.
- `mods/idle-compact`: idle compaction, a server plugin ported from Claude Code. A large main session that has gone idle compacts through OpenCode's `session.compact` shortly before its prompt cache expires (the last request's start plus the cache's lifetime, less a margin). The composition root is `cmd/idle-compact/server.ts`; the decision is `due` in `idle.ts`, the lifetimes in `cache.ts`, the timers in `model.ts`, the contract in `service.ts`, implemented in `opencode/`. `tests/idle-compact.test.ts` proves it in real OpenCode on a 20 s cache; the rules are in the README's Idle compaction section.
- `mods/mail`: session mail, a server plugin. It adds two direct tools (a kernel cell reaches them as `tools.sessions` and `tools.message`): `sessions` lists the server's sessions an agent can write to, and `message({ to, text, wake?, replyTo? })` puts `text` into the session `to` names (an id, or a title), as a steered synthetic message under a header naming the sender and how to answer; an idle receiver wakes unless `wake: false`. To coordinate with another session, list it, message it, and answer a message only when it asks for something. The composition root is `cmd/mail/server.ts`; the rules are in `address.ts`, `directory.ts` and `letter.ts`, the sending in `model.ts`, the contract in `service.ts`, implemented in `opencode/`. `tests/mail.test.ts` proves an exchange and a steer in real OpenCode; the rules are in the README's Session mail section.
- `mods/questions`: background questions, a server and a TUI plugin ported from gent's `ask_user_async`. The server adds the `ask_user_async` tool (a direct tool, so a kernel cell reaches it as `tools.ask_user_async`): the agent asks 1-3 questions, each with the assumption it works on, and carries on at once; an answer arrives later as a steered synthetic message that wakes an idle session and says whether it differs from the assumption. When you can go on with a reasonable assumption, ask with it rather than stopping; when an answer differs, revise the work that rests on it. The TUI draws the tray line above the composer for the session and its subagents and the `/answer` pane, opened by `/answer` or shift+← on an empty composer (`tui/dock.tsx`, `tui/pane.tsx`, `hotkey.ts`). The composition roots are `cmd/questions/server.ts` and `cmd/questions/tui.tsx` (`setup.ts` holds all but its JSX, for the seam test); the model is the `Questions` aggregate in `question.ts`, the sending in `model.ts`, the contracts in `service.ts`, implemented in `opencode/` (the plugin's storage, the session inbox) and `memory/`. `tests/questions.test.ts` proves it in real OpenCode, direct and from a kernel cell; the rules are in the README's Background questions section.
- `mods/wake`: wakes, a server and a TUI plugin ported from gent's `wake`. The server adds four direct tools (a kernel cell reaches them as `tools.wake`, `tools.monitor`, `tools.wake_cancel`, `tools.wake_list`): `wake({ afterSeconds | at, everySeconds?, mode?, note, newSession? })` sets an alarm and `monitor({ command, cwd?, intervalSeconds?, until?, timeoutSeconds?, note })` polls a command; each fires as a steered synthetic message carrying the note (`notify`: no turn, read at the next one; `newSession`: a fresh session with that prompt). Use `wake`/`monitor` for every wake-up: waiting on CI, a deploy, a time of day, a later session. `okra schedule` is no longer needed for them: each entry also registers an OS job (Bun.cron, `bun.cron.opencode-wake-<id>`) that starts the OpenCode service and fires it when no server is running. After setting one, end your turn unless other work remains; a root session may use them, a subagent (any orchestrate role) is refused and waits on a background shell instead. The TUI draws the tray line above the composer (`⏰ 2 wakes · next 14:30`). The composition roots are `cmd/wake/server.ts`, `cmd/wake/tui.tsx` and the OS job's script `cmd/wake/backstop.ts`; the model is `WakesModel` in `model.ts` over the entries in `wake.ts`, the letters in `message.ts`, the contracts in `service.ts` with their laws in `laws.ts`, implemented in `opencode/`, `process/`, `cron/` and `memory/`. `tests/wake.test.ts` runs `scenarios/wake.ts` and `scenarios/wake-downtime.ts`; the rules are in the README's Wakes section.
- `mods/skills`: `$<skill>` mentions with gent's tiers, a server and a TUI plugin. Typing `$` at a word start opens the composer's popup of skills (through the fork's `ui.autocomplete`); a sent `$<id>`, `$<id>:local` or `$<id>:global` token attaches that skill, as an `@` mention does. When the project and the user both have a skill of one id, the server registers `<id>:local` and `<id>:global` and `$<id>` takes the local one. The composition roots are `cmd/skills/server.ts` and `cmd/skills/tui.tsx`; the rules are in `mention.ts`, `tier.ts` and `catalog.ts` (with the skills RPC, `SKILLS`), the model in `model.ts`, the contract in `service.ts`, implemented in `filesystem/`, the popup in `tui/`. `tests/skills.test.ts` runs `scenarios/skills.ts`; the rules are in the README's Skills section.
- `scripts/agents.ts`: `bun run agents` writes `mods/orchestrate/agents.json` from the orchestrate skill (`~/.claude/skills/orchestrate`), so the prompts are Claude Code's word for word; `--check` fails when it is stale. Edit the skill, never the JSON.
- `tests/`: `prime.test.ts` runs `scenarios/prime-demo.ts` and asserts on its frames' text and colours; `workers.test.ts` runs `scenarios/prime-workers.ts` for the background-worker group and completion line. `prime-subagents.test.ts` runs `scenarios/prime-subagents.ts` for moving between a session and its running subagents by keyboard and mouse; `prime-rows.test.ts` runs `scenarios/prime-rows.ts`, with the orchestrate plugin, for the live subagent rows. `prime-sidebar.test.ts` runs `scenarios/prime-sidebar.ts` for the rows staying beneath the composer while the sidebar shows. `prime-pin.test.ts` runs `scenarios/prime-pin.ts` for the ask pinned over the transcript while the reader is scrolled up (`mods/prime/ask.ts`: the prompt the view's top row answers, one line; needs a fork with the `session.transcript.overlay` slot). `prime-wake.test.ts` runs `scenarios/prime-wake.ts` for a worker that waits on its own background shell: its row runs and says what it waits on, and its parent gets the answer it wrote after the shell (needs a fork whose subagent jobs wait for that work). `prime-compaction.test.ts` runs `scenarios/prime-compaction.ts` for a `/compact`: one line at Details and Overview, the host's block and the summary at All (needs a fork with the `session.message.compaction` slot). `gamut.test.ts` and `pty-host.test.ts` cover gamut. `orchestrate.test.ts` checks the role agents against the skill and runs real OpenCode through its SDK (`tests/orchestrate/run.ts`) on a scripted model (`tests/orchestrate/sim.ts`) for the guard, compaction and the Sabbath. `kernel.test.ts` does the same for the kernel (`tests/kernel/`).
- `testbeds/gamut/`: `bun run gamut`, a live run of OpenCode with our plugins against a red fixture app, driven from the shell (`up`, `send`, `wait`, `read`, `status`, `down`). See its README.
- The fork lives at `~/Developer/personal/opencode` (remote `cevr/opencode`, upstream `anomalyco/opencode`), based on the v2.2.5 release commit `4878a0e30f`. Branch `prime-look` carries the TUI plugin hook points the look uses. Keep the fork's diff small and generic (hook points OpenCode lacks); the look itself belongs here.

## Checks
All of them need `OPENCODE_DEV` pointing at the fork checkout.
- `bun run lint`: oxlint; errors are the layout fence.
- `bun run typecheck`: links the fork's `packages/tui/node_modules` entries into every workspace package's `node_modules` (`bun run link-fork`), then checks the root and each `mods/*` and `cmd/*` project. Link before and after `bun install`, which drops the links.
- `bun run test`: the scenario tests. Without `OPENCODE_DEV` they skip and say so.

## Running a scenario
`OPENCODE_DEV=<opencode checkout or rift> SCENARIO_OUT=out OPENCODE_DRIVE_MEDIA_DIR=$PWD/media bunx opencode-drive run scenarios/<name>.ts`
- Without `OPENCODE_DEV` it drives the installed `opencode2`.
- `SCENARIO_LABEL` names the frame and screenshot; `SCENARIO_THEME` picks the theme; `SCENARIO_DUMP=1` writes each model request as `request-<n>.json`.
- The simulated model is offered `patch`, not `edit`, and `shell`, not `bash`.
