# OpenCode mods

Our harness work, ported onto OpenCode 2.x: the Prime Agent look, orchestration, the account pool, the code kernel.

This folder lives in the PUBLIC dotfiles repo: stage by exact path, keep tokens, account labels and run evidence out of it (`out/` and `media/` are ignored). Run every command from `opencode/`.

Before changing a mod, read `ARCHITECTURE.md`: every mod is an Effect program modeled like an alchemy-domain model and laid out like a Go service. A mod is one context and one workspace package (`mods/<mod>`): domain files at its root that own their contracts, implementation folders inside it named after their dependency, and a `cmd/<mod>` package per plugin as the only composition root. oxlint fences the imports (`bun run lint`); `scripts/layout.test.ts` checks the names and lists the mods not yet moved as pending.

## Layout
- `scenarios/`: opencode-drive scenarios. Each runs OpenCode headless with a scripted model and writes frames (text) and screenshots. They are the deterministic check for every UI or plugin change.
- `mods/subagents`: the subagent rows, plain TypeScript with no plugin of its own. `rows(family, rootSessionID, now)` in `subagent-row.ts` gives each subagent's role (the orchestrate step's role noun: the child's role agent, or, for a worker or general child, the role its call's description names in `described.ts`'s form, the role word then dropped from the unit: `verifier opus 5.5  closure-flake r1 (Opus)`; any other worker reads `worker`), model (by its short name, `model.ts`: `opus 5.5`, `sol 6.1`, never the provider or effort), unit, state (working, waiting, blocked, latched, done, failed, cancelled, idle), one-sentence update, time in its state and time since it was last heard from, in launch order, keeping a stopped one `LINGER_MS`. Working: its turn generates or runs a call that works. Waiting: its turn runs a call that only waits (a sleep or poll loop, a shell call whose description opens with wait, poll or sleep, or one that waits on a shell, `action: "wait"`; `shell.ts`), or it ended its turn while a shell it started still runs (the host's shell registry lists it for the session, `Session.shells`) or a subagent under it works. Whether a session works now is `worksNow(family)` in `works.ts`, from the host's live state alone (running, blocked, latched, or idle with a running shell or a working subagent under it, recursively): the rows, the dock's count, the ↓ hint and ←/→ (`working` in `mods/prime/subagent.ts`) all read it, and the fork's Subagents panel (↓) reads the same rule (`sessionActivity`, listing such a subagent as `Waiting`); a transcript call or stop notice only supplies the words, so a notice that never comes (a shell killed by PID or by the agent through its handle, a restart) keeps no row live. Latched: a start orchestrate's pace or the Sabbath holds, kept as a wake (the child's `latch` metadata, `Session.latch`) and not yet started; its update is the hold and when it opens (`pace · opens 14:30`, `Sabbath · opens Sat 18:12` when it opens on another day), timed since it latched, and it counts among the live rows. A cancelled latch reads cancelled, a failed one failed. The update is the running call (a shell call by its `description`, else in a few words, `flock gate.lock ./scripts/gate.sh`, never the one-liner), unless a sentence it wrote, thought or put in its queue is newer; a waiting row with no newer sentence says what it waits on. `format(row, width)` in `line.ts` draws one as coloured segments with no state word, the state the leading diamond, by fill and colour (`SYMBOLS`, `stateTone`): `◆ worker opus 5.5  <unit>  <update> · 12s` or `◈ worker opus 5.5  <unit>  <update> · 37m · updated 26m ago` (the age once 5 min stale), dropping parts from the right as the width shrinks: the age, the model's version, the update, then the cut. Its root files import each other and orchestrate's plain `described.ts` only. Its input is the plain `Family` view in `family.ts`, which `opencode/view.ts` reads from a TUI plugin's `context.data`; a TUI reads it through `familyReader()` in `solid/reader.ts`, one reader for the process: each message's reading, each session's transcript and `Session`, and each root's family are Solid memos, the family shared by every view that reads it (Prime's dock, hints and rows, the queue's sidebar) and disposed once none does, so a streamed token re-reads its own message and rebuilds its own session only, never the whole family (read bare inside a computation, it re-read every part of every message per token, in each of those views: 0.3 to 0.6 of a core for a long session, `tests/tui-cpu.test.ts`). The rows' per-session values (when last heard, the launch call by child, the step count, the sayings) are kept per `Message` and per `messages` list (`once` in `activity.ts`), and `subagents` and `worksNow` once per `Family`, so a token costs O(children), about 1 ms at 170 children of 100 messages (`solid/family.bench.ts`).
- `themes/`, `mods/`: what OpenCode loads from us. `mods/prime` is the Prime look with fx's rail composer and tool-call groups (a header over a `├`/`└` tree per run of calls, after `vercel-labs/fx` as gent copied it: a run is one model step's calls, ended early by answer text, so each kernel cell or batch of parallel calls is its own group and the newest call is the last line, a kernel call draws as the `tools.*` calls its cell made (`kernel.ts`), never its code, under its own `description` as the header when it gave one, and a step's thought is its tree's first node, `├ thinking  <first line>` in faint text below All and the whole thought at All, a thought-only step a one-node group headed `Thought` (`Thinking` while it streams), never at Overview; a subagent call whose result says it latched reads `Latched`), loaded by path through the config's `plugins` as `cmd/prime` (its composition root, `cmd/prime/tui.tsx`). The words each row shows are plain domain files at the mod's root (`group.ts`, `call.ts`, `notice.ts`, `chrome.ts`, ..., over the session values in `session.ts`); the Solid components are in `tui/`, which read the host only through `tui/host.ts`'s `Host`, built from the plugin context in `opencode/host.ts`. Steps that only start background agents, each within a minute of the last, share one group, and a worker or shell completion notice is a tool-call group (through the fork's `session.message.completion` slot, `notice.ts`): `● General finished · <task>` (✗ in the error colour when failed, ● in the warning colour when cancelled) over its result as a `└` body, 5 lines below All, header only at Overview; notices that land side by side fold into one group, `● 3 agents finished`, a `├` node per worker. The host's own mail, question and wake `◈` notices are not ours. A compaction is one line below All (`◇ Compacted automatically · 171k → 6k tokens · 12.0s`, `compaction.ts`: the compaction request's prompt and output tokens, the time to the next message the run writes) and the host's whole block with the summary at All (through the fork's `session.message.compaction` slot, branch `prime-compaction-row` until it lands on `prime-look`). The dock's shell count opens the session's shell list by click (`shells.ts`, `opencode/shells.ts`: state, runtime and last line per shell, ctrl+k kills one), and a shell call the host moved to the background ends its row with `moved to the background` (see the README's Background shells). A subagent's row, a finished worker's notice and the dock's subagent count open by click (the row and notice open that session, the count the host's Subagents picker); inside a subagent the top bar names its parent, ↑ goes back and ←/→ move to the other running subagents, and the hint above the composer says so; in the main session `↓ subagents` sits under the composer, at the left of the dock's first line (model · usage at its right). The dock reads `◆ N subagents  ·  N shells  ·  2 wakes · 1 monitor` (a latched subagent counts among the subagents, never the wakes; the wakes only while any are pending or notices unread, `wakes.ts`, read over the wake mod's RPC in `opencode/wakes.ts`), and is not drawn at all, no row and no blank, while no subagent works, no shell runs and no wake or monitor is pending and no notice is unread (`dockShown` in `chrome.ts`). ↓ on an empty prompt opens the host's composer panel, where Prime adds Wakes and Monitors tabs after the host's Subagents, Shell and Terminals (through the fork's `ui.composerTab`, `tui/composer.tsx`, the row and detail words in `wakes.ts`): a row per pending alarm (`◇ <note>  wake · once  pending  in 9m 59s`) or monitor (`◆ <command>  <newest output line>  watching  40s  checked 0s ago`), soonest first, in the panel's columns (`panel.ts`, `tui/panel.tsx`, which also draw the panel's tab bar, the host tabs' rows and the footer through the fork's `session.composer.panel.*` slots, branch `panel-slots`), ↑/↓ to move, Enter for the whole entry in the host's alert, ctrl+d to cancel it over the wake mod's `cancel` RPC, `No pending wakes` / `No monitors` when empty; a tab's keys are a `composer` keymap layer the Host binds (`composerKeys`), live only while the tab is mounted (active); a session goal (the fork's `/goal`) shows only as one state-coloured line right above the composer (`goal.ts`, `GoalLine`: active `● goal · <objective> · N↻ · /goal pause · /goal cancel`, paused `‖ goal paused · <reason> · /goal resume · /goal cancel`, met muted for 10 s), never in the dock. The dock shows no Escape hint.tsx`, from `mods/subagents`) gives its state as its leading diamond, no word (working pulses `◆`/`◇`, a second each, turning with its time on one tick so an idle orchestrator paints about once a second (`tests/tui-paint.test.ts`), in the success colour; waiting `◈`, blocked `◆` and cancelled `◇` still in the warning colour; latched `◇` in the info colour; idle `◇` and done `◆` muted; failed `◆` in the error colour), its role, its model's short name (`opus 5.5`, the version dropping first as the row narrows), its unit, a one-sentence update, its time in that state and, when stale, its last update's age, a finished one lingering 30 seconds, whether or not the host shows the session's sidebar; inside a subagent the rows sit above the host's picker and mark the one shown. The domain imports only `effect` and `@dotfiles/opencode-subagents/*`, `opencode/` may import the wake protocol file `@dotfiles/opencode-wake/wake`, and `tui/` never `@opencode/*` or `opencode/` (`.oxlintrc.json` fences); OpenCode provides `@opencode/plugin`, `@opentui/*` and `solid-js` and compiles the TSX, workspace imports included, at load time.
- `mods/orchestrate`: the orchestrate skill's rules, a server plugin. It defines the role agents (planner, implementor, verifier, worker) from `agents.json`, runs untyped and general subagent calls as the worker, one of those or a `worker` call whose description names a step in the skill's form (`<role> <unit> r<N>`, or `<unit>[ rN] <role>[ rN][ (note)]`; `described.ts`) as that role, and former role names as the role, while a follow-up naming no particular agent keeps its child's (logging each call and why, `described` for the description, to `~/.cache/orchestrate/opencode-agents.jsonl`), writes each role's start and hand-back (the first line of its last answer) to its unit's `log.md` through the skill's `log.ts --current` (`unit-log.ts`; no unit dir found, nothing written), gives every role and primary agent one fixed 400k compaction window (`WINDOW` in `compaction.ts`), runs a worker asked or inheriting `#max` at its model's default effort unless its description ends `(mechanical)` (`capEffort` in `role.ts`; the log's `lowered` and the parent's answer say so), and stops agent work over the Sabbath. The worker's prompt (`agents/worker.md`) carries the roles' first-compaction handoff: write a handoff file and end `compacted: <path>`, so the parent starts a fresh worker. Opus first, Codex second: daily binds every role to the newest Opus, and puts a new planner start that names no model on the newest Fable first (the `planner` option, `firstOf` in `model.ts`; held or not offered it takes Opus, then Codex, its line saying why in `first`; over the Sabbath it latches on Fable like every role on its own, and its open takes that chain; no other role ever starts on Fable), and a new start the pace holds (with no `model` named; a role start naming the role's own model, at any variant, counts as naming none, logged `model-dropped`) starts at once on Codex's newest sol, or luna at max for a `(light)`, `(direct)` or `(mechanical)` description (`codexFallback` in `role.ts`), when the Codex pace admits it; the call log's `call` line and the parent's answer say why (`fallback`). A new subagent start that the Sabbath holds, or that both paces hold, latches instead of being refused: the wakes keep it as a `latch` entry under the parent with its child session made unprompted, the call (foreground or background, or a kernel cell's `tools.subagent`) answers at once that it is latched, why and when it opens, and at its time the wakes ask orchestrate's opener (`OPENER`, `openLatch` in `model.ts`) to decide it again, Opus first, then the fallback: still held on both latches again (a pace at most every `PACE_POLL_MS`, 120 s), admitted starts it in the background on that child, and its result wakes the parent. Only with no wakes plugin is a held start refused (`PaceHeld`, with the time it opens). The window takes effect through the fork's per-agent compaction threshold (`request.settings.compactionWindow`). A root that owns a run (it started one of the run's steps) and ends its turn while the run holds units in plan, implement or verify, or units in `ready` whose batch is due (by each unit's cadence, which the skill's `status.ts` prints from its spec's `Batch cadence`, else its plan's, else 3 ready or the oldest ready 30 min by its `log.md` time), is steered once per idle period with `idle with units in plan, implement or verify: <units>; start them or name what you wait on.` and, for a due batch, `batch due (<why>): <units>; land it with rift({ action: "land", rifts: ["<run>/<unit>", …] }).`, each Rift by its branch (`riftOf` in `idle.ts`), unless a subagent or shell still runs, the owner drafts a prompt to it (reported by the TUI half, `cmd/orchestrate/tui.ts`), a wake or open question holds it, or it named its wait as a `waiting` queue item; `tests/idle-root.test.ts` runs `scenarios/idle-root.ts`. The same idle tells such a root once per skill version when the installed orchestrate skill (git, `git/skill.ts`) is newer than the version its run last saw (`<run dir>/skill-version`, `filestore/run-records.ts`): the commit subjects since, the run's `Departs from` lines, and to reconcile its rules files (`skill-drift.ts`, `SkillDrifts` in `model.ts`; the README's A run that saw an older skill).
  The composition roots are `cmd/orchestrate/server.ts` and `cmd/orchestrate/tui.ts`; the model is the `ToolCall` aggregate in `tool-call.ts`, the contracts in `service.ts`, implemented in `filestore/`, `opencode/` and `codex/`. Its model is in the README's Orchestrate section.
- `mods/pool`: the account pool, a server plugin. It chooses the login each request of a pooled provider goes out on, holds a refused login and fails over to another; other mods read it over `status.ts` (`@dotfiles/opencode-pool/status`). The composition root is `cmd/pool/server.ts`; the model is the `AccountPool` aggregate in `account-pool.ts`, the contracts in `service.ts`, implemented in `opencode/` and `gent/`. Its model is in the README's Pool section.
- `mods/status`: the `/pool` pane, a server and a TUI plugin. The server answers the status RPC (`status.ts`) with the live subagents from orchestrate's call log and each orchestrate run's units; the pane (`tui/pane.tsx`) draws them beside the pool's status. The composition roots are `cmd/status/server.ts` and `cmd/status/tui.tsx`; the model is the `AgentCalls` view in `agent-calls.ts` and the handler in `model.ts`, the contracts in `service.ts`, implemented in `filestore/` and `process/`. Its model is in the README's Status section.
- `mods/queue`: the agent's live queue, a server and a TUI plugin. The server adds the `queue` tool (a direct tool, so a kernel cell reaches it as `tools.queue`), keeps each session's queue in a file store and answers the queue RPC (`queue.ts`, `QUEUE`); the sidebar's Queue section (`tui/sidebar.tsx`) shows the route's root session's queue items only, one line each, an item linked to a subagent session marked with that session's live state. The composition roots are `cmd/queue/server.ts` and `cmd/queue/tui.tsx`; the model is the `Queue` aggregate in `queue.ts`, the board in `board.ts`, the contract in `service.ts`, implemented in `filestore/` and `memory/`; `opencode/subagents.ts` maps the shared rows of `@dotfiles/opencode-subagents` to the live state of each subagent session. Its model is in the README's Queue section.
- `mods/git`: the sidebar's Git section and the `/git` pane, a server and a TUI plugin ported from gent's `@gent/git`. The server answers the git RPC (`git.ts`) by running git and `gh` in the session's directory (its location, read per call); the TUI runs no program except the review it hands the terminal to (hunk, else git's pager) through the renderer's suspend and resume. The composition roots are `cmd/git/server.ts` and `cmd/git/tui.tsx`; the parsers are in `checkout.ts` and `pull-request.ts`, the handler in `model.ts`, the contracts in `service.ts`, implemented in `process/` and `opencode/`. The server also offers the `pr` tool and runs its per-machine watcher (`pr.ts`, `pulls.ts`, the `PrWatch` and `DefaultBranch` deciders in `watch.ts` and `branch.ts`, GitHub in `process/github.ts`); `Pulls.poke(repo)` is the seam for a push source. `tests/git.test.ts` runs `scenarios/git.ts`, `tests/pr.test.ts` runs `scenarios/pr.ts`. Its model is in the README's Git section.
- `mods/btw`: `/btw`, a side question in the session's panel, a TUI plugin ported from gent's `/btw` with no server half. `/btw <question>` forks the session (`session.fork`, which keeps its cache key) and asks the fork with a hidden note; the pane reads the fork from the server's message list (`opencode/readings.ts`; the TUI's message cache evicts sessions it does not retain), follows up, and ctrl+s brings the newest answer back as a steered synthetic. The fork's built-in `/btw` is off (`-opencode.btw` in `cli.json`). The composition root is `cmd/btw/tui.tsx` (`setup.ts` holds everything but the JSX, for the seam test); the model is the `SideQuestion` aggregate in `side-question.ts`, the handlers in `model.ts`, the contracts in `service.ts`, implemented in `opencode/` and `memory/`, the controller and pane in `tui/`. `tests/btw.test.ts` runs `scenarios/btw.ts`. Its model is in the README's Btw section.
- `decider/` (`@dotfiles/decider`): what the mods' domains share. `decider.ts` is the aggregate's `Decider` type and `fold`; `story.ts` runs a Decider's stories (`Story.make(decider)(given, clock, when, then, rejected, state, view)`); `tool-input.ts` is `toolInput(struct)`, which every tool input our plugins add is wrapped in: the model sees the struct's own JSON Schema, and a numeric string in a number field or a JSON-array string in an array field decodes as that number or list. A tool's number fields take `Schema.Finite` or `Schema.Int`, never `Schema.Number`, whose JSON Schema adds an `"Infinity"`/`"NaN"` string branch; `scripts/tool-inputs.test.ts` holds every `cmd/*/server.ts` input to both.
- `cmd/`: one workspace package per plugin OpenCode loads (`server.ts`, `tui.tsx`); `bun run daily` loads a plugin from `cmd/<mod>` once it exists, else from `mods/<mod>`.
- `sim/` (`@dotfiles/opencode-sim`): the simulated OpenCode host for server plugins. One seed drives a virtual clock, the order of fibers and same-instant timers, and every id; our real composition roots (`cmd/<mod>/server.ts`) run on it together, on its plugin context, on memory alone (`world.ts`; the rules in `host.ts`, the context in `context.ts`, the scheduler in `runtime.ts`, the plugins as loaded in `plugins.ts`). A restart closes each plugin's scope and builds it again from its root on the same stores. A simulated test is a `*.sim.test.ts` beside its composition root, run by the seed runner (`seed.ts`: 20 seeds, `SIM_SEED=<n>` replays one, 5 s of wall time a file); it never reads wall time (`static.test.ts`). Every operation the world's context offers is named by a host law (`host-laws.ts`), run on the world (`host-laws.test.ts`) and on real OpenCode (`tests/host-laws.test.ts`, through `tests/host-laws/real.ts` and the law probe plugin `server.ts`); add a law with any new operation. A real acceptance test moves onto the world only through `tests/parity.json` (`scripts/accept-parity.test.ts`). See its README.
- `mods/anthropic-auth`: the Claude subscription login, vendored from `@ex-machina/opencode-anthropic-auth` (MIT) with our quota readings and the seam the pool chooses each request's credential through; provenance in its README. The composition root is `cmd/anthropic-auth/server.ts`; the domain is one concept per file at the mod's root, the decisions (logins, refreshes, readings) in `model.ts`, the contracts in `service.ts` with their laws in `laws.ts`, implemented in `fetch/`, `node/`, `registry/` and `opencode/`. `cmd/anthropic-auth/server.test.ts` drives the plugin on a stand-in host. Its tests run without `ANTHROPIC_BASE_URL`.
- `mods/kernel`: the code kernel, a server plugin ported from gent's `cell`. The `kernel` tool runs TypeScript in a Bun worker per session (`worker/program.ts`, framed over fd 3 and 4 by `wire.ts`) whose bindings persist and are stored after each call; `tools.<name>()` inside it runs the session's other tools (`opencode/toolbox.ts`), and each call records them, live and in its result's metadata (`operations` in `operations.ts`), for the transcript. A cell's `tools.shell({ command })` only runs a command and resolves to a live shell handle (`worker/shell-handle.ts`: `.read`, `.wait`, `.kill`, `.refresh`); `tools.shell.handle(id)` rebuilds one and `tools.shell.list()` gives one per shell, and an input with an action other than `run`, or a field that acts on a shell (`id`, `ms`, `offset`, `lines`, the older `kill`, `wait`, `list`), throws, naming the method; the methods call the tool with its actions (`check`, `wait`, `kill`, `list`). A cell's `tools.subagent(input)` resolves to a live subagent handle (`worker/subagent-handle.ts`: `.wait`, `.stop`, `.read`, `.refresh`; `tools.subagent.handle(sessionID)`, `tools.subagent.list()`) over the `subagents` tool the plugin adds beside the kernel (`subagents.ts`, `opencode/subagents.ts`: list, get, wait, stop a session's own descendants, refusing any other; a stop is the host's `session.stop` (fork), ending the subagent's turn, its shells and queued prompts). The composition root is `cmd/kernel/server.ts`; the model is the `KernelSession` aggregate among the domain files at the mod's root. By default it is the agent's runtime (the fork's `options.runtime`): the model sees only the kernel, and calls go through the registry's hooks. Its description lists each tool on one line (`catalog` in `tools.ts`; the full words through `tools.docs(name)` and `tools.docs.search(query)`, BM25 in `bm25.ts` over an index built once per set of tools, `summary.ts`) and is frozen per session at its first request (`frozen.ts`, put back by the request hooks; a later change in the tools is a synthetic notice, never a new description), so the cached prefix holds. Options and limits are in the README.
- `mods/herdr`: the herdr reporter, a TUI plugin ported from gent's `@gent/herdr`. - `mods/cache`: prompt-cache misses, a TUI plugin ported from gent's `@gent/cache` and a server plugin, the request ledger. It folds a session's assistant messages (`opencode/view.ts`) into the prefixes a step was billed for again (`scan` in `miss.ts`, above a 1,024-token floor), gives each its cause over the cache lifetime its agent's request used (`ttl.ts`: the agent's `request.settings.cacheTTL` over a configured `settings.cache.ttl`, else that, else Anthropic 5 min, OpenAI 30 min), naming a pool login move (the pool's `logins` RPC) and a compaction apart from a changed prefix, prices it (`price.ts`), and draws a row after each turn's footer slot for a miss of 20k tokens or $0.10 (a compaction's summary request's after the compaction's slot, never in a turn's) and a sidebar line `Cache 91% · missed $0.42 · expired` (the costliest cause last) for the session and its subagents (`line.ts`, `ledger.ts`, `tui/`). The server half fingerprints each primary and compaction request in `http.request` (`fingerprint.ts`: tools, system paragraphs and message parts hashed, never a message's text kept), judges it against the session's request before when its step ends (`request-log.ts`: first, hit, uncached, model, expired, login, compaction, prefix with the first changed segment, unchanged; `model.ts`), appends a line to `~/.cache/opencode-cache-ledger/ledger.jsonl` and keeps the session's newest request beside it (`last/<sessionID>.json`, read back by a copy that has judged nothing of the session, so the first request after a restart is judged against the last one before it, its line `restored`) (the `RequestLog` contract in `service.ts`, its laws in `laws.ts`, implemented in `filestore/` and `memory/`), and answers the TUI over the `dotfiles-opencode.cache` RPC, which refines a changed prefix (`refine` in `ledger.ts`). `scripts/cache-ledger.ts` sums the ledger (`summary.ts`); `scripts/cache-audit.ts` audits it for the dream (`audit.ts`: hit rate, write cost share, breaks found from the tokens and classified by cause; `--static`, `rules.ts`: the six caching rules from source probes and the window's breaks). The composition roots are `cmd/cache/tui.tsx` and `cmd/cache/server.ts` (seam test `server.test.ts`); `tests/cache.test.ts` runs `scenarios/cache.ts` and `scenarios/cache-compaction.ts` with both halves.
- `mods/rift`: the `rift` tool, a server plugin. It replaces OpenCode's worktree tools (`opencode_worktree_create`, `_list`, `_remove`, removed from the registry in its transform) with one direct tool (`tools.rift` from a kernel cell): `{ action: "create", branch, name?, source? }` makes a Rift of the session's warm source on the branch (`rift create --copy-all` and a branch switch on the Mac, `workrift create` on the workbox) and answers its directory, branch and how to `session_move` there; `{ action: "list" }` lists the source's Rifts with their unsaved work; `{ action: "remove", name | path, force? }` trashes one, refusing (unless `force`) one with uncommitted changes, stashes or commits found nowhere else, and always a warm source, the session's own Rift and a Rift with Rifts of its own (`withChildren` takes its own Rifts too); `{ action: "land", rifts }` lands the Rifts as one batch in the source's `integrate` Rift (merge each in order, lock and `rift.generated` conflicts written again, one `rift.gate`, one push, the Rifts trashed, then one `rift.accept` in the background that wakes the session, then the repository's `rift.postLand` step in the source's `post-land` Rift, which wakes it with its report; the gate and accept always run heavy, through the guard's launcher). A post-land step is owed from the push until it has run, one per warm source (`owed.ts`): it runs at once when no load reading in the last 5 minutes was at or past the host's cores, else the plugin's minute check runs it once the load has settled 5 minutes, and a land runs one owed 6 hours whatever the load; a later land's replaces the one owed (one run, the newest head with the oldest owed base), and the owed steps survive a restart in `post-land-owed.json` (`filestore/debts.ts`). ## Checks
All of them need `OPENCODE_DEV` pointing at the fork checkout.
- `bun run gate`: the gate every change passes before push, a few seconds (`scripts/gate.ts`). It links the fork, then runs lint, `agents --check`, the typecheck of every project and the unit tests (every `*.test.ts` outside `tests/`: `mods/**`, `cmd/**` with the simulated `*.sim.test.ts`, `decider/**`, `sim/**` and `scripts/`, which holds the layout check, the parity check and `bun run daily`'s tests) at once. A unit test file that passed is skipped while nothing it reaches changed (`scripts/reach.ts`: its package, the packages that package depends on, and the shared inputs: root manifest, lock file, configs, Bun, the fork), so a change to a shared package re-runs its dependents' tests. `bun scripts/gate.ts --all` ignores that cache (`node_modules/.cache/gate/`).
- `bun run accept`: the acceptance tests (`tests/*.test.ts`), real OpenCode on a scripted model: a parallel pool as wide as the host's load leaves free, then the files marked `// accept: one at a time (<why>)` one by one. Mark a new acceptance file that asserts an upper bound on a time, rate or CPU; one that only waits for events (under generous deadlines) stays in the pool. `scripts/accept.test.ts` names a bounding file that lacks the marker. `bun run accept:affected [base]` runs only the files that reach a file changed since `base` (default: the merge base with origin/main); a change to a shared input runs them all. `--list` prints each phase and its files without running them. Only `bun run gate` blocks a push. Right after the push, run `accept:affected <the pre-merge base>` in the background (a full `accept` after a fork change), and fix any red at once, before other work. Without `OPENCODE_DEV` the real-OpenCode tests skip and say so.
- `bun run lint`: oxlint, then the Effect debt ratchet (`scripts/effect-debt.ts --check`). oxlint's errors are the layout fence, the `oxlint-plugin-effect` rules kept as errors (the production domain's six among them), and the repo's own rules in `lint/`: `dotfiles/no-module-env-in-tests`, and `dotfiles/kept-suite-folders` (every `tests/` file but `tests/scratch.ts` takes its temp folders from `scratch()`, and a suite holding a Kept makes its folders through it: no `tmpdir()`, no recursive `mkdir`, `cp`, `mkdtemp` or path-making `Bun.write` there). The ratchet holds every other recommended Effect rule at its per-file budget in `effect-debt.json`, except `noComments`, which it drops (a style preference, not an error class); see the README's lint section.
- `bun run typecheck`: links the fork's `packages/tui/node_modules` entries into every workspace package's `node_modules` (`bun run link-fork`), then checks the root and each `mods/*`, `cmd/*` and the `sim` project, all at once. Link before and after `bun install`, which drops the links.
- `bun run test`: every test file, unit and acceptance, one after another (the old full run, about nine minutes).

## Running a scenario
`OPENCODE_DEV=<opencode checkout or rift> SCENARIO_OUT=out OPENCODE_DRIVE_MEDIA_DIR=$PWD/media bunx opencode-drive run scenarios/<name>.ts`
- Without `OPENCODE_DEV` it drives the installed `opencode2`.
- `SCENARIO_LABEL` names the frame and screenshot; `SCENARIO_THEME` picks the theme; `SCENARIO_DUMP=1` writes each model request as `request-<n>.json`.
- The simulated model is offered `patch`, not `edit`, and `shell`, not `bash`.
