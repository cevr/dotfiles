# OpenCode mods

Our harness work, ported onto OpenCode 2.x: the Prime Agent look, orchestration, the account pool, the code kernel.

This folder lives in the PUBLIC dotfiles repo: stage by exact path, keep tokens, account labels and run evidence out of it (`out/` and `media/` are ignored). Run every command from `opencode/`.

Before changing a mod, read `ARCHITECTURE.md`: every mod is an Effect program modeled like an alchemy-domain model and laid out like a Go service. A mod is one context and one workspace package (`mods/<mod>`): domain files at its root that own their contracts, implementation folders inside it named after their dependency, and a `cmd/<mod>` package per plugin as the only composition root. oxlint fences the imports (`bun run lint`); `scripts/layout.test.ts` checks the names and lists the mods not yet moved as pending.

## Layout
- `scenarios/`: opencode-drive scenarios. Each runs OpenCode headless with a scripted model and writes frames (text) and screenshots. They are the deterministic check for every UI or plugin change.
- `themes/`, `mods/`: what OpenCode loads from us. `mods/prime` is the Prime look with fx's rail composer and tool-call groups (a header over a `├`/`└` tree per run of calls, after `vercel-labs/fx` as gent copied it: a run is one model step's calls, ended early by answer text, so each kernel cell or batch of parallel calls is its own group and the newest call is the last line, a kernel call draws as the `tools.*` calls its cell made (`kernel.ts`), never its code, under its own `description` as the header when it gave one, and a step's thought is its tree's first node, `├ thinking  <first line>` in faint text below All and the whole thought at All, a thought-only step a one-node group headed `Thought` (`Thinking` while it streams), never at Overview; a subagent call whose result says it latched reads `Latched`), loaded by path through the config's `plugins` as `cmd/prime` (its composition root, `cmd/prime/tui.tsx`). The words each row shows are plain domain files at the mod's root (`group.ts`, `call.ts`, `notice.ts`, `chrome.ts`, ..., over the session values in `session.ts`); the Solid components are in `tui/`, which read the host only through `tui/host.ts`'s `Host`, built from the plugin context in `opencode/host.ts`. Steps that only start background agents, each within a minute of the last, share one group, and a worker or shell completion notice is a tool-call group (through the fork's `session.message.completion` slot, `notice.ts`): `● General finished · <task>` (✗ in the error colour when failed, ● in the warning colour when cancelled) over its result as a `└` body, 5 lines below All, header only at Overview; notices that land side by side fold into one group, `● 3 agents finished`, a `├` node per worker. The host's own mail, question and wake `◈` notices are not ours. A compaction is one line below All (`◇ Compacted automatically · 171k → 6k tokens · 12.0s`, `compaction.ts`: the compaction request's prompt and output tokens, the time to the next message the run writes) and the host's whole block with the summary at All (through the fork's `session.message.compaction` slot, branch `prime-compaction-row` until it lands on `prime-look`). The dock's shell count opens the session's shell list by click (`shells.ts`, `opencode/shells.ts`: state, runtime and last line per shell, ctrl+k kills one), and a shell call the host moved to the background ends its row with `moved to the background` (see the README's Background shells). A subagent's row, a finished worker's notice and the dock's subagent count open by click (the row and notice open that session, the count the host's Subagents picker); inside a subagent the top bar names its parent, ↑ goes back and ←/→ move to the other running subagents, and the hint above the composer says so. The dock reads `◆ N subagents  ·  N shells  ·  2 wakes · 1 monitor` (a latched subagent counts among the subagents, never the wakes; the wakes only while any are pending or notices unread, `wakes.ts`, read over the wake mod's RPC in `opencode/wakes.ts`); a session goal (the fork's `/goal`) shows only as one state-coloured line right above the composer (`goal.ts`, `GoalLine`: active `● goal · <objective> · N↻ · /goal pause · /goal cancel`, paused `‖ goal paused · <reason> · /goal resume · /goal cancel`, met muted for 10 s), never in the dock. Beneath the dock's subagent count, one live row per subagent of the family (`tui/live.tsx`, from `mods/subagents`) gives its state as its leading diamond, no word (working pulses `◆`/`◇`, 600 ms each, in the success colour; waiting `◈`, blocked `◆` and cancelled `◇` still in the warning colour; latched `◇` in the info colour; idle `◇` and done `◆` muted; failed `◆` in the error colour), its role, its model's short name (`opus 5.5`, the version dropping first as the row narrows), its unit, a one-sentence update, its time in that state and, when stale, its last update's age, a finished one lingering 30 seconds, whether or not the host shows the session's sidebar; inside a subagent the rows sit above the host's picker and mark the one shown. The domain imports only `effect` and `@dotfiles/opencode-subagents/*`, `opencode/` may import the wake protocol file `@dotfiles/opencode-wake/wake`, and `tui/` never `@opencode/*` or `opencode/` (`.oxlintrc.json` fences); OpenCode provides `@opencode/plugin`, `@opentui/*` and `solid-js` and compiles the TSX, workspace imports included, at load time.
- `mods/subagents`: the subagent rows, plain TypeScript with no plugin of its own. `rows(family, rootSessionID, now)` in `subagent-row.ts` gives each subagent's role (the orchestrate step's role noun: the child's role agent, or, for a worker or general child, the role its call's description names in `described.ts`'s form, the role word then dropped from the unit: `verifier opus 5.5  closure-flake r1 (Opus)`; any other worker reads `worker`), model (by its short name, `model.ts`: `opus 5.5`, `sol 6.1`, never the provider or effort), unit, state (working, waiting, blocked, latched, done, failed, cancelled, idle), one-sentence update, time in its state and time since it was last heard from, in launch order, keeping a stopped one `LINGER_MS`. Working: its turn generates or runs a call that works. Waiting: its turn runs a call that only waits (a sleep or poll loop, or a shell call whose description opens with wait, poll or sleep; `shell.ts`), or it ended its turn while a shell it started still runs (the host's shell registry lists it for the session, `Session.shells`) or a subagent under it works. Whether a session works now is `worksNow(family)` in `works.ts`, from the host's live state alone (running, blocked, latched, or idle with a running shell or a working subagent under it, recursively): the rows, the dock's count, the ↓ hint and ←/→ (`working` in `mods/prime/subagent.ts`) all read it, and the fork's Subagents panel (↓) reads the same rule (`sessionActivity`, listing such a subagent as `Waiting`); a transcript call or stop notice only supplies the words, so a notice that never comes (a shell killed by PID or shell_kill, a restart) keeps no row live. Latched: a start orchestrate's pace or the Sabbath holds, kept as a wake (the child's `latch` metadata, `Session.latch`) and not yet started; its update is the hold and when it opens (`pace · opens 14:30`, `Sabbath · opens Sat 18:12` when it opens on another day), timed since it latched, and it counts among the live rows. A cancelled latch reads cancelled, a failed one failed. The update is the running call (a shell call by its `description`, else in a few words, `flock gate.lock ./scripts/gate.sh`, never the one-liner), unless a sentence it wrote, thought or put in its queue is newer; a waiting row with no newer sentence says what it waits on. `format(row, width)` in `line.ts` draws one as coloured segments with no state word, the state the leading diamond, by fill and colour (`SYMBOLS`, `stateTone`): `◆ worker opus 5.5  <unit>  <update> · 12s` or `◈ worker opus 5.5  <unit>  <update> · 37m · updated 26m ago` (the age once 5 min stale), dropping parts from the right as the width shrinks: the age, the model's version, the update, then the cut. Its root files import each other and orchestrate's plain `described.ts` only. Its input is the plain `Family` view in `family.ts`, which `opencode/view.ts` reads from a TUI plugin's `context.data`. Prime's live rows use it, and the sidebar Queue is meant to.
- `mods/orchestrate`: the orchestrate skill's rules, a server plugin. It defines the role agents (planner, implementor, verifier, worker) from `agents.json`, runs untyped and general subagent calls as the worker, one of those or a `worker` call whose description names a step in the skill's form (`<role> <unit> r<N>`, or `<unit>[ rN] <role>[ rN][ (note)]`; `described.ts`) as that role, and former role names as the role, while a follow-up naming no particular agent keeps its child's (logging each call and why, `described` for the description, to `~/.cache/orchestrate/opencode-agents.jsonl`), gives each role its compaction window from `~/.cache/orchestrate/compact.json`, and stops agent work over the Sabbath. A new subagent start that the pace or the Sabbath holds latches instead of being refused: the wakes keep it as a `latch` entry under the parent with its child session made unprompted, the call (foreground or background, or a kernel cell's `tools.subagent`) answers at once that it is latched, why and when it opens, and at its time the wakes ask orchestrate's opener (`OPENER`, `openLatch` in `model.ts`) to decide it again: still held latches again (a pace at most every `PACE_POLL_MS`, 120 s), admitted starts it in the background on that child, and its result wakes the parent. Only with no wakes plugin is a held start refused (`PaceHeld`, with the time it opens). The window takes effect through the fork's per-agent compaction threshold (`request.settings.compactionWindow`).
  The composition root is `cmd/orchestrate/server.ts`; the model is the `ToolCall` aggregate in `tool-call.ts`, the contracts in `service.ts`, implemented in `filestore/`, `opencode/` and `codex/`. Its model is in the README's Orchestrate section.
- `mods/pool`: the account pool, a server plugin. It chooses the login each request of a pooled provider goes out on, holds a refused login and fails over to another; other mods read it over `status.ts` (`@dotfiles/opencode-pool/status`). The composition root is `cmd/pool/server.ts`; the model is the `AccountPool` aggregate in `account-pool.ts`, the contracts in `service.ts`, implemented in `opencode/` and `gent/`. Its model is in the README's Pool section.
- `mods/status`: the `/pool` pane, a server and a TUI plugin. The server answers the status RPC (`status.ts`) with the live subagents from orchestrate's call log and each orchestrate run's units; the pane (`tui/pane.tsx`) draws them beside the pool's status. The composition roots are `cmd/status/server.ts` and `cmd/status/tui.tsx`; the model is the `AgentCalls` view in `agent-calls.ts` and the handler in `model.ts`, the contracts in `service.ts`, implemented in `filestore/` and `process/`. Its model is in the README's Status section.
- `mods/queue`: the agent's live queue, a server and a TUI plugin. The server adds the `queue` tool (a direct tool, so a kernel cell reaches it as `tools.queue`), keeps each session's queue in a file store and answers the queue RPC (`queue.ts`, `QUEUE`); the sidebar's Queue section (`tui/sidebar.tsx`) shows the route's root session's queue items only, one line each, an item linked to a subagent session marked with that session's live state. The composition roots are `cmd/queue/server.ts` and `cmd/queue/tui.tsx`; the model is the `Queue` aggregate in `queue.ts`, the board in `board.ts`, the contract in `service.ts`, implemented in `filestore/` and `memory/`; `opencode/subagents.ts` maps the shared rows of `@dotfiles/opencode-subagents` to the live state of each subagent session. Its model is in the README's Queue section.
- `mods/git`: the sidebar's Git section and the `/git` pane, a server and a TUI plugin ported from gent's `@gent/git`. The server answers the git RPC (`git.ts`) by running git and `gh` in the session's directory (its location, read per call); the TUI runs no program except the review it hands the terminal to (hunk, else git's pager) through the renderer's suspend and resume. The composition roots are `cmd/git/server.ts` and `cmd/git/tui.tsx`; the parsers are in `checkout.ts` and `pull-request.ts`, the handler in `model.ts`, the contracts in `service.ts`, implemented in `process/` and `opencode/`. `tests/git.test.ts` runs `scenarios/git.ts`. Its model is in the README's Git section.
- `mods/btw`: `/btw`, a side question in the session's panel, a TUI plugin ported from gent's `/btw` with no server half. `/btw <question>` forks the session (`session.fork`, which keeps its cache key) and asks the fork with a hidden note; the pane reads the fork from the server's message list (`opencode/readings.ts`; the TUI's message cache evicts sessions it does not retain), follows up, and ctrl+s brings the newest answer back as a steered synthetic. The fork's built-in `/btw` is off (`-opencode.btw` in `cli.json`). The composition root is `cmd/btw/tui.tsx` (`setup.ts` holds everything but the JSX, for the seam test); the model is the `SideQuestion` aggregate in `side-question.ts`, the handlers in `model.ts`, the contracts in `service.ts`, implemented in `opencode/` and `memory/`, the controller and pane in `tui/`. `tests/btw.test.ts` runs `scenarios/btw.ts`. Its model is in the README's Btw section.
- `decider/` (`@dotfiles/decider`): what the mods' domains share. `decider.ts` is the aggregate's `Decider` type and `fold`; `story.ts` runs a Decider's stories (`Story.make(decider)(given, clock, when, then, rejected, state, view)`).
- `cmd/`: one workspace package per plugin OpenCode loads (`server.ts`, `tui.tsx`); `bun run daily` loads a plugin from `cmd/<mod>` once it exists, else from `mods/<mod>`.
- `mods/anthropic-auth`: the Claude subscription login, vendored from `@ex-machina/opencode-anthropic-auth` (MIT) with our quota readings and the seam the pool chooses each request's credential through; provenance in its README. The composition root is `cmd/anthropic-auth/server.ts`; the domain is one concept per file at the mod's root, the decisions (logins, refreshes, readings) in `model.ts`, the contracts in `service.ts` with their laws in `laws.ts`, implemented in `fetch/`, `node/`, `registry/` and `opencode/`. `cmd/anthropic-auth/server.test.ts` drives the plugin on a stand-in host. Its tests run without `ANTHROPIC_BASE_URL`.
- `mods/kernel`: the code kernel, a server plugin ported from gent's `cell`. The `kernel` tool runs TypeScript in a Bun worker per session (`worker/program.ts`, framed over fd 3 and 4 by `wire.ts`) whose bindings persist and are stored after each call; `tools.<name>()` inside it runs the session's other tools (`opencode/toolbox.ts`), and each call records them, live and in its result's metadata (`operations` in `operations.ts`), for the transcript. A cell reaches the background-shell tools as `tools.shell_list`, `tools.shell_read` and `tools.shell_kill`. The composition root is `cmd/kernel/server.ts`; the model is the `KernelSession` aggregate among the domain files at the mod's root. By default it is the agent's runtime (the fork's `options.runtime`): the model sees only the kernel, and calls go through the registry's hooks. Options and limits are in the README.
- `mods/herdr`: the herdr reporter, a TUI plugin ported from gent's `@gent/herdr`. Inside a herdr pane it reports the current route's root session and its subagents to herdr's socket as idle, working or blocked (source `dotfiles:opencode`, resume `opencode -s <root>`), with the session's title and the running tool as labels. The composition root is `cmd/herdr/tui.tsx`; the decision is `decide` in `activity.ts`, the contract `Herdr` in `service.ts`, implemented over the socket in `herdr/socket.ts`; `opencode/view.ts` reads the TUI's data. `tests/herdr.test.ts` runs `scenarios/herdr.ts` against a fake herdr socket.
- `mods/cache`: prompt-cache misses, a TUI plugin ported from gent's `@gent/cache` with no server half. It folds a session's assistant messages (`opencode/view.ts`) into the prefixes a step was billed for again (`scan` in `miss.ts`, above a 1,024-token floor), gives each its cause over the cache lifetime its agent's request used (`ttl.ts`: the agent's `request.settings.cacheTTL` over a configured `settings.cache.ttl`, else that, else Anthropic 5 min, OpenAI 30 min), naming a pool login move (the pool's `logins` RPC) and a compaction apart from a changed prefix, prices it (`price.ts`), and draws a row after each turn's footer slot for a miss of 20k tokens or $0.10 and a sidebar line `Cache 91% · missed $0.42` for the session and its subagents (`line.ts`, `ledger.ts`, `tui/`). The composition root is `cmd/cache/tui.tsx`; `tests/cache.test.ts` runs `scenarios/cache.ts`.
- `mods/guard`: the destructive-command guard, a server plugin ported from Claude Code's `claude/hooks/guard-destructive.ts` with gent's guard-floor parsing. Its `execute.before` hook refuses a `shell`/`bash` call that loses work for good (recursive `rm` of root, home, the working directory, `.git` or a repository root; `git reset --hard`; a forced wide `git clean`), direct or from a kernel cell. The composition root is `cmd/guard/server.ts`; the decision is `verdict` in `verdict.ts`, the contracts in `service.ts`, implemented in `filesystem/` and `opencode/`. `tests/guard.test.ts` proves both paths in real OpenCode; the rules are in the README's Guard section.
- `mods/idle-compact`: idle compaction, a server plugin ported from Claude Code. A large main session that has gone idle compacts through OpenCode's `session.compact` shortly before its prompt cache expires (the last request's start plus the cache's lifetime, less a margin). The composition root is `cmd/idle-compact/server.ts`; the decision is `due` in `idle.ts`, the lifetimes in `cache.ts`, the timers in `model.ts`, the contract in `service.ts`, implemented in `opencode/`. `tests/idle-compact.test.ts` proves it in real OpenCode on a 20 s cache; the rules are in the README's Idle compaction section.
- `mods/mail`: session mail, a server plugin. It adds two direct tools (a kernel cell reaches them as `tools.sessions` and `tools.message`): `sessions` lists the server's sessions an agent can write to, and `message({ to, text, wake?, replyTo? })` puts `text` into the session `to` names (an id, or a title), as a steered synthetic message under a header naming the sender and how to answer; an idle receiver wakes unless `wake: false`. To coordinate with another session, list it, message it, and answer a message only when it asks for something. The composition root is `cmd/mail/server.ts`; the rules are in `address.ts`, `directory.ts` and `letter.ts`, the sending in `model.ts`, the contract in `service.ts`, implemented in `opencode/`. `tests/mail.test.ts` proves an exchange and a steer in real OpenCode; the rules are in the README's Session mail section.
- `mods/questions`: background questions, a server and a TUI plugin ported from gent's `ask_user_async`. The server adds the `ask_user_async` tool (a direct tool, so a kernel cell reaches it as `tools.ask_user_async`): the agent asks 1-3 questions, each with the assumption it works on, and carries on at once; an answer arrives later as a steered synthetic message that wakes an idle session and says whether it differs from the assumption. When you can go on with a reasonable assumption, ask with it rather than stopping; when an answer differs, revise the work that rests on it. The TUI draws the tray line above the composer for the session and its subagents and the `/answer` pane, opened by `/answer` or shift+← on an empty composer (`tui/dock.tsx`, `tui/pane.tsx`, `hotkey.ts`). The composition roots are `cmd/questions/server.ts` and `cmd/questions/tui.tsx` (`setup.ts` holds all but its JSX, for the seam test); the model is the `Questions` aggregate in `question.ts`, the sending in `model.ts`, the contracts in `service.ts`, implemented in `opencode/` (the plugin's storage, the session inbox) and `memory/`. `tests/questions.test.ts` proves it in real OpenCode, direct and from a kernel cell; the rules are in the README's Background questions section.
- `mods/wake`: wakes, a server plugin ported from gent's `wake`. The server adds four direct tools (a kernel cell reaches them as `tools.wake`, `tools.monitor`, `tools.wake_cancel`, `tools.wake_list`): `wake({ afterSeconds | at, everySeconds?, mode?, note, newSession? })` sets an alarm and `monitor({ command, cwd?, intervalSeconds?, until?, timeoutSeconds?, note })` polls a command; each fires as a steered synthetic message carrying the note (`notify`: no turn, read at the next one; `newSession`: a fresh session with that prompt). Use `wake`/`monitor` for every wake-up: waiting on CI, a deploy, a time of day, a later session. `okra schedule` is no longer needed for them: each entry also registers an OS job (Bun.cron, `bun.cron.opencode-wake-<id>`) that starts the OpenCode service and fires it when no server is running. After setting one, end your turn unless other work remains; a root session may use them, a subagent (any orchestrate role) is refused and waits on a background shell instead. A third kind, `latch` (`latch.ts`), is a subagent start orchestrate holds: set over the `latch` RPC, opened through the `Opener` contract, listed by `wake_list`, cancelled by `wake_cancel`, kept and backstopped like an alarm; it marks its child's `latch` metadata, which the subagent rows read. Prime's dock shows the alarms and monitors after the shells (`2 wakes · 1 monitor`), reading the `pending` RPC; a latch shows as its subagent's row instead. The composition roots are `cmd/wake/server.ts` and the OS job's script `cmd/wake/backstop.ts`; the model is `WakesModel` in `model.ts` over the entries in `wake.ts`, the letters in `message.ts`, the contracts in `service.ts` with their laws in `laws.ts`, implemented in `opencode/`, `process/`, `cron/` and `memory/`. `tests/wake.test.ts` runs `scenarios/wake.ts` and `scenarios/wake-downtime.ts`; the rules are in the README's Wakes section.

## Checks
All of them need `OPENCODE_DEV` pointing at the fork checkout.
- `bun run gate`: the gate every change passes before push, a few seconds (`scripts/gate.ts`). It links the fork, then runs lint, `agents --check`, the typecheck of every project and the unit tests (every `*.test.ts` outside `tests/`: `mods/**`, `cmd/**`, `decider/**` and `scripts/`, which holds the layout check and `bun run daily`'s tests) at once. A unit test file that passed is skipped while nothing it reaches changed (`scripts/reach.ts`: its package, the packages that package depends on, and the shared inputs: root manifest, lock file, configs, Bun, the fork), so a change to a shared package re-runs its dependents' tests. `bun scripts/gate.ts --all` ignores that cache (`node_modules/.cache/gate/`).
- `bun run accept`: the acceptance tests (`tests/*.test.ts`), real OpenCode on a scripted model, every file in parallel (about two minutes). `bun run accept:affected [base]` runs only the files that reach a file changed since `base` (default: the merge base with origin/main); a change to a shared input runs them all. `--list` prints the files without running them. Only `bun run gate` blocks a push. Right after the push, run `accept:affected <the pre-merge base>` in the background (a full `accept` after a fork change), and fix any red at once, before other work. Without `OPENCODE_DEV` the real-OpenCode tests skip and say so.
- `bun run lint`: oxlint; errors are the layout fence.
- `bun run typecheck`: links the fork's `packages/tui/node_modules` entries into every workspace package's `node_modules` (`bun run link-fork`), then checks the root and each `mods/*` and `cmd/*` project, all at once. Link before and after `bun install`, which drops the links.
- `bun run test`: every test file, unit and acceptance, one after another (the old full run, about nine minutes).

## Running a scenario
`OPENCODE_DEV=<opencode checkout or rift> SCENARIO_OUT=out OPENCODE_DRIVE_MEDIA_DIR=$PWD/media bunx opencode-drive run scenarios/<name>.ts`
- Without `OPENCODE_DEV` it drives the installed `opencode2`.
- `SCENARIO_LABEL` names the frame and screenshot; `SCENARIO_THEME` picks the theme; `SCENARIO_DUMP=1` writes each model request as `request-<n>.json`.
- The simulated model is offered `patch`, not `edit`, and `shell`, not `bash`.
