# How a step ends

Generated by `scripts/ending.ts` from its two functions: edit that, then run `scripts/agents.ts`. F1 gives each item's label from its own state; F2 gives the verdict and its files from the item states present, and the evidence from why the step stopped. Each role's prompt carries its own tables, as below.

## planner

**How your step ends.** It stops the moment a refusal comes (the Refusals paragraph) or the round's limit passes; else it goes on until no runnable item is left. Each item is in one state, decided by its own history, and that state alone gives its label, whatever stopped the step (first table). The states present give your verdict and its files (second table), and why the step stopped gives the evidence they hold. Effort is no state and no label. Your required work: every section of the spec filled, and its acceptance check runnable and recorded red. You never implement, so the product behavior its Done line names stays unbuilt and is no item left.

| State | An item that is | Its label |
| --- | --- | --- |
| done | done; for a check, ran and passed | none: it is no item left |
| runnable | runnable, not yet run | `continues next round`: this unit's work, in its next round (or its rewrite after the failure cap); never a follow-up |
| waiting | waiting on an open unit, question, commitment or two contradicting spec lines | `waits on <id>` |
| refused | the item the refusal stopped | `refused: <what>`, adding `; form: <the form it named>` only when the refusal named one: this unit's work, never a follow-up, never tried another way |
| cannot run | unable to run on this host: its check or tool is absent or will not start, with no refusal | `cannot run here: <check or tool>`, with its command and output |
| a discovery | work no spec item asks for | `finding outside the unit`, under Follow-ups in your file |

| Verdict, the first that holds | When | You write |
| --- | --- | --- |
| `ready` | every item is done or a discovery | `<unit dir>/spec.md` |
| `blocked` | otherwise | `<unit dir>/state.md` current (even with no commit since) and `<unit dir>/blocked.md`: the stop's evidence, and each item left with its label |

The stop's evidence: a refusal named an accepted form: what was refused and the form it named (the exact `!` command or allow rule, as Refusals says); a refusal named no accepted form: what was refused, as the refusal said it, and an allow rule only if one exists; the round's limit passed: the clock (the timebox) or the count (the failure cap); no runnable item is left: what you tried for each item that holds the step back, the options and your pick.

## verifier

**How your step ends.** It stops the moment a refusal comes (the Refusals paragraph); else it goes on until no runnable item is left. Each item is in one state, decided by its own history, and that state alone gives its label, whatever stopped the step (first table). The states present give your verdict and its files (second table), and why the step stopped gives the evidence they hold. Effort is no state and no label. Your required work: every check of step 1 ran to a result that settles pass or fail, for every unit; a check of step 1 that could not run or ran unclear is `stuck`, never `accepted`, and a wider probe this host cannot run goes under Unproven and does not stop `accepted`. Before any unit, a `Heads: dotfiles=<sha> fork=<sha>` line must name your head and its fork commit (`git rev-parse`), else the batch is `stuck`. The batch: `stuck` on a wrong heads line, else `accepted` if every unit is, `changes` if any is, else `stuck`.

| State | An item that is | Its label |
| --- | --- | --- |
| done | done; for a check, ran and passed | none: it is no item left |
| proven | a check that ran and proves a Blocker or Major | a Blocker or Major, filed with its proof |
| runnable | runnable, not yet run | `not run`, named under Check |
| waiting | waiting on an open unit, question, commitment or two contradicting spec lines | `waits on <id>` |
| refused | the item the refusal stopped | `refused: <what>`, adding `; form: <the form it named>` only when the refusal named one: never tried another way |
| cannot run | unable to run on this host: its check or tool is absent or will not start, with no refusal | `cannot run here: <check or tool>`, with its command and output |
| ran unclear | a required check that ran, but whose result cannot establish pass or fail | `ran unclear: <check>`, with its command and the output that settles nothing |
| a unit finding | a weak test, narrowed acceptance or written-rule break with no failing run that the unit's change introduced, shown by measured attribution (whether or not a spec item names it) | marked `unit`: the same lane closes it in its next round |
| a base finding | such a finding the base head shows too | marked `base`: a follow-up unit |

| Verdict, the first that holds | When | You write |
| --- | --- | --- |
| `stuck` | any item is runnable, waiting, refused, cannot run or ran unclear | each unit's `round-N-findings.md` and the batch's findings file; under Check, the stop's evidence, and each item left with its label |
| `changes` | any item is proven | each unit's `round-N-findings.md` and the batch's findings file, with each item left with its label |
| `accepted` | otherwise | each unit's `round-N-findings.md` and the batch's findings file, with each item left with its label |

The stop's evidence: a refusal named an accepted form: what was refused and the form it named (the exact `!` command or allow rule, as Refusals says); a refusal named no accepted form: what was refused, as the refusal said it, and an allow rule only if one exists; no runnable item is left: each check that holds the verdict back, with its command and exit code.
