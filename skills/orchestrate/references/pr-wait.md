# Waiting on a team approval

Where main changes only through a PR that a teammate approves (a team repo, `Lands: PR`), a ready unit lands like any other, except that main never moves: the batch gate runs once, locally, on the merged batch; each unit's own branch is pushed and its PR opened or updated as a draft (`create-pr`); CI on the PR starts as the spec's `CI` line names (Land a batch, step 4); and the batch verifier verifies the merged head. A teammate never reviews a change the verifier has not accepted. Once it accepts the unit, mark its PR ready for review (`gh pr ready`), request its reviewers, and log `verify → waiting(pr)`. It holds no slot: start the next unit. Run one background until-loop on `gh pr view <n> --json reviewDecision,state` that exits when either changes. Approved with CI green on the PR's current head: it merges on GitHub, then log `waiting(pr) → merged <hash>` and close the unit. Changes requested, or a red CI run: log `waiting(pr) → implement r<N+1>`, and the comments or failures go to its implementor as the next round on the same branch; its next batch gates and verifies it before the PR is updated and marked ready again. Without the `waiting(pr)` state, the wait for approvals reads as time spent in verify, and the logs cannot tell it from work.
