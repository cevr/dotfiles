# Waiting on a team approval

Where main changes only through a PR a teammate approves (a team repo, `rift.push false`, `Lands: PR`), units run in batch mode and main never moves. The land's merge check runs once, locally, on the merged batch; each unit's own branch is pushed (never forced; a stack's layers through `gh stack`) and its PR opened or updated as a draft (`create-pr`). CI on the PRs starts as the spec's `CI` line names; where it starts on a comment, comment once the stack is quiet, after its last push, on its top PR, naming the suites the diff needs, and again after a later push. The batch's verifier verifies the merged head: a teammate never reviews a change the verifier has not accepted.

Once the verifier accepts a unit, mark its PR ready (`gh pr ready`), request its reviewers, and log `verify → waiting(pr)`. It holds no slot: start the next unit. Run one background until-loop on `gh pr view <n> --json reviewDecision,state` that exits when either changes. Approved with CI green on the PR's head: it merges on GitHub; log `waiting(pr) → merged <hash>` and close the unit. Changes requested, or a red CI run: log `waiting(pr) → implement r<N+1>`, and the comments or failures go to its implementor as the next round on the same branch. A rebase that keeps the same `git patch-id` keeps the verdict; a changed patch is verified again before the PR goes ready. Without `waiting(pr)`, the wait for approvals reads as time in verify.
