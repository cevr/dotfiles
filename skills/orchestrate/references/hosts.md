# Hosts: starting, moving and waiting on a role

Read this before the first wave, and when a role is held or moves family. The role table and the effort policy are in [`SKILL.md`](../SKILL.md#roles-on-each-host).

- **Worker type.** On Claude Code, each role in the table passes its own agent type: `subagent_type: "orchestrate-planner"`, `"orchestrate-implementor"`, `"orchestrate-reviewer"` or `"orchestrate-verifier"` (owner, 2026-10-24). Each carries `protocol.md`'s shared sections, its role's section and the safety rules in its prompt, so it reads neither file, and it holds the knowledge across a compaction. Each role is its own agent kind with its own tuned compaction window (on 2026-10-24, reviewers 160k and implementors 120k; a role with fewer than 20 transcripts takes `orchestrate-worker`'s). `scripts/agents.ts` writes the four agents for both hosts from `protocol.md` and `loop/safety.md` (`agents/` for Claude Code, `codex/agents/` for Codex, linked to `~/.codex/agents`); the gate fails while they differ. On Codex, each role passes the same name as `agent_type`; the agent file sets the role's effort, which wins over a Codex spawn's, and no file pins a model. A Claude Code orchestrator's `mcp__codex__start` effort wins over the file's. Any other agent the run starts (an exploration agent, a look prototype) passes `subagent_type: "orchestrate-worker"` (owner, 2026-10-21): 9 tools and a one-paragraph prompt instead of `general-purpose`'s full tool list, MCP servers included, so each turn rereads a smaller context. Each role's call, an `Agent` call or an `mcp__codex__start`, has a `description` that starts like its hand-back line, `<role> <unit> r<N>` (`implementor sheet r2`): the model eval joins a worker or a Codex thread to its unit and round by it. In the week of 2026-10-17 the model eval guessed the role from free-form descriptions and got 33 of 131 workers wrong.

- **Families.** Every role runs on the host's own family unless its row says otherwise, and the review always comes from the family the implementor is not. From Claude Code the reviewer is that other family itself and reviews directly, with no counsel run: a Codex thread on the newest sol, or Opus for a unit a Codex thread implemented (owner, 2026-10-25), at the effort SKILL.md's one effort policy sets. From Codex, which starts no Claude agent, the reviewer agent sends its packet through `okra counsel`, which routes to Claude on Opus at `medium`, and validates what comes back. **Work never waits long on one family** (owner, 2026-10-28: "if we have to wait hours or days, then just use Opus and vice versa"). A hold of a few minutes is fine; past 10 minutes the role moves to the other family. A Codex `start` or `send` that comes back `queued`: run `codex-bridge wait <thread> --patience 10` in the background. Exit 0 means the turn started. Exit 4 means it is still latched or the bridge is down: interrupt the thread with `mcp__codex__interrupt` and start the role as its Claude row (an implementor as a fresh Opus implementor with consolidated scope, a reviewer as Opus with `review directly`). A held `Agent` call: run its waiter as `budget.ts --wait <ticket> --patience 10`. Exit 4 means the Claude pool is still held: start the role as a Codex thread by `mcp__codex__start` (planner and reviewer on `sol`, implementor on `luna` or `sol` for a UI unit, verifier on `luna`). A hold that names an opening time more than 10 minutes away moves at once. The review still comes from the family the implementor is not, wherever the implementor now runs; when only one family is open, the review runs on it, and its fresh context keeps it independent. Log each move in the unit's Decisions (`implementor r<N> on Opus: Codex latched`). Never Fable. The verifier's independence comes from its fresh context, the clean checkout and the pre-written check.

- **Fresh implementor.** Round 2 goes to the same implementor while it has not compacted: its context and prompt cache make the fix round a delta. A worker ends `blocked compacted` at its first compaction (`protocol.md`, Ending a step). From round 3, or after that hand-back, stop it and start a fresh one with consolidated scope: the spec, every `round-*-findings.md` and `round-*-verify.md`, `state.md`, the branch, and the unit's Decisions lines. Past one compaction the kept context is mostly stale and every turn rereads it: rive-core held 5 compactions over 1,403 turns at about 190k context a turn (266M cache-read), while talk1b's fresh R1 was accepted in one round.

- **Fresh reviewers and verifiers.** They start fresh each round, so they never anchor on what they said before. The findings carry forward as files.

- **Codex threads** (Claude Code orchestrator). The `codex` mod (`~/Developer/personal/dotfiles/claude/mods/codex`) runs Codex workers as threads of one `codex app-server` per host, held by the `codex-bridge` daemon. Load its tools with ToolSearch (`select:mcp__codex__start,mcp__codex__send,mcp__codex__interrupt,mcp__codex__threads`). `start` takes the same `description` as an `Agent` call, the role, and a model family (`luna`, `sol`) that resolves to its newest release; the thread carries the role agent's instructions from `codex/agents/`. `send` is round 2 on the same thread, so its context and cache carry over. `mcp__codex__threads` shows each thread's context fill and compactions (the fresh-implementor rule above applies to a thread as to an agent) and the Codex plan's usage window. The Luna `standard` implementor is a trial, which `models.ts` judges by round-1 accepts and rounds per unit: keep it only while those hold against Opus. A reviewer thread is fresh each round: a new `start`, never `send`. The review still crosses families: a unit a Codex thread implemented gets the Opus reviewer (Families).

- **Waiting.** Claude Code: background agents and background shell commands wake you when they finish, and a Codex thread's finished turn arrives as a message from the codex plugin, with its final message. Codex (`[features] multi_agent = true`, `[agents] max_threads = 12`): a subagent's final status reaches you as a notification. Call `wait_agent` only when nothing else can move. Nobody polls: no sleep loops, and no reading a worker's transcript to check progress.

- **Messages are files** ([`protocol.md`](../protocol.md), Messages). You talk to a worker only through the host's agent messages, naming file paths; a terminal pane is never a transport.

## The model eval

`bun ~/.claude/skills/orchestrate/scripts/models.ts` is the model eval. For each phase and model, from Claude Code and Codex transcripts, it prints the cost, minutes, tokens and compactions, and what the phase produced: units merged (plan), round-1 accepts (implement), changes and escapes to verify (review), fails (verify), and units merged per session (decide). It joins a worker to its unit by the hand-back line, so keep that line exact. A model with no price prints `?`; one row in `scripts/models/prices.ts` prices it.
