# Hosts: starting, moving and waiting on a role

Read this before the first wave, and when a role is held or falls back to Codex. The role table and the effort policy are in [`SKILL.md`](../SKILL.md#roles-on-each-host). OpenCode is the main host; Claude Code and Codex follow.

- **OpenCode** (an OpenCode orchestrator). Every role is a native `subagent` call with `agent` set to the role (`agent: "verifier"`), never `general` or `worker`, and a `description` that starts like the hand-back line (`verifier auth r1`). The role agent carries the protocol and the role's effort; the worker carries neither. The orchestrate mod runs a general or worker call whose description names a role (`<role> <unit> r<N>`) as that role, but name the agent anyway. The config binds every role to the newest Opus, and the mod starts a new planner on the newest Fable first; pass no `model`, since a call that names one runs on it as is, with no fallback. A `worker` call at `#max`, named or inherited from your session, runs at the model's default effort unless its description ends `(mechanical)`; bulk model work (a critique of many images) is a script, not a worker at max. When the pace holds a new Fable planner start, the mod starts it on Opus; when it holds a new Opus start, the mod starts it at once on Codex's newest sol (high; the verifier medium), if the Codex pace admits it; a held implementor, worker or other agent latches for its own model instead, and the spend-evenly pace alone never holds it; the answer says it runs on the Codex fallback and why. There are no Codex threads or Codex tools: round 2 to the same implementor is a `subagent` call with its `sessionID`, and a verifier is a new call each batch. A new subagent held on both, or by the Sabbath, is latched, not refused: the call answers at once with its `sessionID`, why it waits and when it opens; it starts by itself in the background on whichever opens first, and its result wakes you like a background subagent's. Do not start it again, send to it, poll or wait for it; `wake_list` shows the latch and `wake_cancel` cancels it. A held call that answers with an error and an opening time had no latch: start it again after then. Keep the run's live items in the `queue` tool.

- **Worker type** (Claude Code and Codex). On Claude Code, each role in the table passes its own agent type: `subagent_type: "planner"`, `"implementor"`, or `"verifier"`. Each carries `protocol.md`'s shared sections, its role's section and the safety rules in its prompt, so it reads neither file, and it holds the knowledge across a compaction. Each role is its own agent kind with its own compaction window, which `budget.ts --tune` writes: the planner, the implementor and the verifier at 400k, since each holds the plan or spec, the code it reads and the output of what it runs in one context, and `worker` at 200k. `scripts/agents.ts` writes the three agents for both hosts from `protocol.md` and `loop/safety.md` (`agents/` for Claude Code, `codex/agents/` for Codex, linked to `~/.codex/agents`); the gate fails while they differ. On Codex, each role passes the same name as `agent_type`, and every `spawn_agent` passes `fork_turns: "none"`: the default, `all`, starts the worker on the orchestrator's whole history, so it is neither fresh nor small. The agent file sets the role's effort, which wins over a Codex spawn's, and no file pins a model. A Claude Code orchestrator's `mcp__codex__start` effort wins over the file's. Any other agent the run starts (an exploration agent, a look prototype) passes `subagent_type: "worker"`: 9 tools and a one-paragraph prompt instead of `general-purpose`'s full tool list, MCP servers included, so each turn rereads a smaller context. Each role's call, an `Agent` call or an `mcp__codex__start`, has a `description` that starts like its hand-back line, `<role> <unit> r<N>` (`implementor auth r2`): the model eval joins a worker or a Codex thread to its unit and round by it. A free-form description leaves the eval guessing the role, and it guesses wrong often.

- **Fable plans, Opus first for the rest, Codex second.** The planner runs on the newest Claude Fable at medium, and on the newest Opus when the Claude pool holds a new Fable start (Fable's own week spent, or the pool's pace). Every other role, the verifier too, runs on the newest Claude Opus at its row's effort, on every host that can start one. Codex is the fallback for a planner or verifier, for when the Claude pool holds a new Opus start, never a default. Codex never implements: a held implementor waits for Opus, and the spend-evenly pace alone never holds one:
  - **OpenCode.** The orchestrate mod does it for you (OpenCode, above).
  - **Claude Code.** A planner's `Agent` call passes `model: "fable"`; held, call `Agent` again with `model: "opus"`. A held Opus `Agent` call starts the role at once by `mcp__codex__start`: a planner or verifier on `sol`. A held implementor waits on `budget.ts --wait <ticket>` alone. When that start comes back `queued` too, run both waiters in the background, `budget.ts --wait <ticket>` and `codex-bridge wait <thread>`, and take whichever exits 0 first: Claude's first, interrupt the thread with `mcp__codex__interrupt` and call `Agent` again; Codex's first, stop the Claude waiter.
  - **Codex.** The fallback host: prefer an OpenCode or Claude Code orchestrator. On Codex only planners and verifiers spawn, and a verifier reviews directly like every verifier; implementation waits for an OpenCode or Claude Code orchestrator.
  - A role already on Codex stays there for its next round (`send`, or a `subagent` call with its `sessionID`); the next new start tries its first model again (Fable for a planner, Opus for the rest). Log each move in the unit's Decisions (`verifier batch-2 on sol: Claude pool held`, `planner auth on Opus: Fable week spent`). Never Sonnet.
  - **Fable is the planner's.** The orchestrate mod's `planner` option (written by `daily.ts`: the newest Fable in the catalog, never a pinned id; the owner's call, 2026-11-12, which ended the half-and-half A/B of 2026-11-10) starts every new planner call that names no model on Fable at the planner's effort, and a follow-up keeps its model. Held or not offered, the start takes the role's chain (Opus, then Codex) and its call-log line says why (`first: { model, fellBack }`). Over the Sabbath a planner latches on Fable like every role on its own model, never moved to Opus, and its open after the Sabbath takes the same chain. An implementor, verifier or worker never starts on Fable, and Fable is never an overflow tier: it draws Opus's 5h and 7d windows as well as its own week. `models.ts --experiment` still shows the finished A/B from the lines that carry an arm (from 2026-11-10 until the switch); new lines carry none.

- **Fresh implementor.** Round 2 goes to the same implementor: its context and prompt cache make the fix round a delta. A compaction does not end a worker's step, in any role: OpenCode compacts in the background, so the agent goes on from its summary and re-reads the spec and `state.md` (`protocol.md`); never start a fresh agent because one compacted. From round 3, stop it and start a fresh one with consolidated scope: the spec, every `round-*-findings.md`, `state.md`, the branch, and the unit's Decisions lines.

- **Fresh verifiers.** One verifier per batch, started fresh, so it never anchors on what an earlier batch's verifier said. The findings carry forward as files.

- **Codex threads** (Claude Code orchestrator, the fallback). The `codex` mod (`~/Developer/personal/dotfiles/claude/mods/codex`) runs Codex workers as threads of one `codex app-server` per host, held by the `codex-bridge` daemon. Load its tools with ToolSearch (`select:mcp__codex__start,mcp__codex__send,mcp__codex__interrupt,mcp__codex__threads`). `start` takes the same `description` as an `Agent` call, the role, and a model family (`luna`, `sol`) that resolves to its newest release; the thread carries the role agent's instructions from `codex/agents/`. `send` is round 2 on the same thread, so its context and cache carry over. `mcp__codex__threads` shows each thread's context fill and compactions (the fresh-implementor rule above applies to a thread as to an agent) and the Codex plan's usage window. A verifier thread is fresh each batch: a new `start`, never `send`.

- **Waiting.** OpenCode: background subagents and background shells wake you when they finish, a latched subagent's result wakes you when it runs, and an outside event (CI, a deploy, a time of day) is one `monitor({ command, until, note })` or `wake({ afterSeconds | at, note })`, a watch over something that changes more than once (several PRs' reviews, a queue) one `monitor({ command, repeat: "change", note })` or the `pr` tool's watch; end your turn after setting it. OpenCode's own schedule tools are removed: each fire was a whole user prompt. Claude Code: background agents and background shell commands wake you when they finish, and a Codex thread's finished turn arrives as a message from the codex plugin, with its final message. Codex (`[features] multi_agent = true`, `[agents] max_threads = 12`): a subagent's final status reaches you as a notification. Call `wait_agent` only when nothing else can move. Nobody polls: no sleep loops, no reading a worker's transcript to check progress, and no message asking how it is going, since a message restarts an idle agent.

- **Messages are files** ([`protocol.md`](../protocol.md), Messages). You talk to a worker only through the host's agent messages, naming file paths; a terminal pane is never a transport.

## The model eval

`bun ~/.claude/skills/orchestrate/scripts/models.ts` is the model eval. For each phase and model, from the running OpenCode service's sessions and from Claude Code and Codex transcripts, it prints the cost, minutes, tokens and compactions, and what the phase produced: units merged (plan), round-1 accepts (implement), changes (verify), and units merged per session (decide). It joins a worker to its unit by the hand-back line, so keep that line exact; a batch's verifier (`verifier batch-<k> r1`) counts once per unit of its batch, each with that unit's own `round-N-findings.md` verdict. A model with no price prints `?`; one row in `scripts/models/prices.ts` prices it.
